# Load test

Generated by `python -m eval.load` against the real backend and PostgreSQL, with
the LLM replaced by `eval.stub_llm` (a fixed 0.5 s per call) and the LLM caches off, so every request runs
retrieval, SQL execution and the fact check. It measures the platform, not the
model provider: a hosted LLM adds its own latency and rate limits on top.

- **Run:** 2026-11-19 15:12 UTC
- **Setup:** one uvicorn worker, Docker Desktop on an Apple-silicon Mac (10 CPUs, 8 GB), PostgreSQL 16 in the same Compose network
- **Requests per level:** 80

## What it shows

- **The floor is the model.** Each answer makes two LLM calls (SQL, then the
  written answer), so the stub alone costs 1.0 s. The platform adds about 60 ms
  at one user and about 1.3 s at 80 concurrent users, with no errors.
- **One worker goes a long way.** Throughput keeps rising to about 29 answers a
  second at 80 users. Run more uvicorn workers to go further, but note that the
  LLM caches live in each process, so a cache hit in one worker does not help
  another.
- **The real limit is the provider.** Groq's free tier allows 8,000 tokens a
  minute and 200,000 a day, about 28 full answers a day. Set
  `DAILY_QUERY_LIMIT` and `DAILY_VISITOR_QUERY_LIMIT` before sharing a public
  link.

Reproduce: start `python -m eval.stub_llm`, point a backend at it with
`LLM_BASE_URL`, turn the LLM caches off, then run `python -m eval.load`.
